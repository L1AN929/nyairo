# Agent Note: G2 explore-d2 薄入口与 10 分钟检查节拍

Status: implemented

## Problem

G2 explore-c 的唯一真实批在 2026-11-03 17:02 CST 以
`BATCH_ABORTED / PROVIDER_OR_TRANSPORT_FAILURE` 停批（第三次 Decision 记录
`DECISION_ATTEMPT_FAILED:MODEL_TIMEOUT`），5 次预留后未形成合格 H，影子比较没有开始。
C 的 30 分钟检查节拍意味着 90 分钟采集窗内只有很少几次定时检查机会；在同样的 7200 秒
总窗与 cap 30 下，要再观察一次自然 H 与同轮双合法，需要一个**新身份、新根、10 分钟检查
节拍**的封闭后继批，而不是重开 C 或改写 C 的根。另有一个账目问题：C 的 prereg 把
「跨批累计 1000」和「单根每 UTC 日 300」混在同一个 `total_cap` 字段里，后继批需要
显式区分，但不改全局 UTC 保险丝。

## Decision

1. `scripts/g2_next_live.py` 新增 `D2_PROFILE`（`g2-explore-20261103-d2`，批键 `d2`）：
   历史 239、cap 30 = 采集 8 + 影子 20（10 对）+ 保留 2、不做承接；根为
   `root/{main,memory-authority,branches}` 平铺布局；总窗 7200、采集 5400、观察 60 秒
   ≤91 次；绝对 21:00 CST 停新请求、19:00 CST 最晚启动。a/b/C 的常量、默认 profile、
   20 对/52 口径一条未改。
2. `LiveProfile` 增加两个可选字段，旧批缺省 `None` 即完全不动：
   - `check_interval_minutes`：D2 为 10。prepare 成功后把该值写进嵌套 Life 实例的持久
     `environment`（`CHIYO_AUTONOMOUS_CHECK_INTERVAL_MINUTES`）；`live_env`（真实路径）
     显式写同一个值，夹具路径仍是 0。audit 同时报告配置值与持久值，不一致按
     `IDENTITY_MISMATCH` 拒绝。这只增加定时检查机会，不改首次故障停锁，也不承诺网关
     抗抖动；机会数不是请求数。
   - `cumulative_total`：D2 为 1000。prereg 的 `history` 同时写 `total_cap`（跨批累计）
     与 `utc_day_cap`（单根 UTC 保险丝），`LifeRequestBudget` 仍只用 300，不改全局常量。
3. 新增 `scripts/g2_explore_d2.py` 薄入口：只 import `g2_explore_c` 的共享实现，注入
   D2 profile/批键；`offline-check/prepare/audit/run/status` 五个命令与 C 同义。
   为支持这点，`g2_explore_c.py` 的实验计划、短链、额度门、单元收集模式、CLI 五处
   改为显式 `profile` 参数，缺省仍是 C，C 的命令行与输出结构不变。
4. D2 的离线检查只跑一条共享短正式链（真实 Supply/M0/runtime、tick 维护 trace、10 对
   影子、20→21/30→31 前拒）与四类出站硬拒，不重做 C 的 observer on/off 对照和旧套件。
5. 新增 `tests/test_g2_explore_d2.py`（8 例）：D2 身份/额度/时限、旧批不变、
   真实 prepare 的持久 10 与 live_env 10/夹具 0、audit 持久值、身份篡改拒绝、
   正式根/自定义根前拒、启动线与截止前拒、缺 endpoint/占位 endpoint 前拒。

## Alternatives considered

- **重开或复用 C 的根/身份，只改一个检查间隔常量**：最强理由是零新根、零新身份，
  一次改动就能再跑。否决原因：C 已经真实启动过并写了 `started`/窗口/账本，复用等于
  在已失败批次上二 run，违反「失败不退、不二 run」与「唯一身份」；改 C 的常量还会把
  历史批次参数一起改写。
- **只把 10 分钟写进 prereg/命令行 env，不改实例持久配置**：最强理由是不碰实例文件、
  改动最小。否决原因：`build_binding` 以嵌套实例的持久 `environment` 为来源，父进程
  临时 export 会被 owner 子进程/重装配覆盖回 30；没有持久值就无法证明 runtime 实际
  生效，也无法在 audit 里核对。
- **把跨批累计 1000 直接塞进 `LifeRequestBudget.utc_day_max`**：最强理由是预算口径
  单一、代码不新增字段。否决原因：那会把「每 UTC 日 300」的保险丝改成 1000，等于
  放宽安全上限；D2 只需要账目区分，不需要新的执行额度。

## Consequences

- D2 的「检查节拍 10 分钟」有三处可核证据：实例持久 `environment`、`live_env` 返回值、
  audit 的配置值/持久值对照；C/a/b 不受影响，夹具环境仍是 0。
- `g2_explore_c.py` 的五个入口签名多了 keyword-only 参数，但默认值保持 C，原命令与
  输出结构不变；D2 只是换 profile 的薄壳，没有第二套控制器。
- prereg 的 `history` 多了 `utc_day_cap` 字段，旧批读旧键 `total_cap` 不受影响；
  `caps` 多了 `check_interval_minutes`/`cumulative_total` 两个标量，旧批为 `null`。
- 仍未验证：真实模型自然 H、真实同轮双合法、发送边界的历史 text 送达、10 对选择差异。
  离线脚本 Decision/内容是替身；D2 真实 prepare/run 由父级另批执行，失败不二 run。
