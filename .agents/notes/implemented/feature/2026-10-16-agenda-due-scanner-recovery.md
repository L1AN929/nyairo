# Agent Note: 待办事项基于前置条件恢复：不做死板的定时器轮询，避免发疯自激

Status: implemented

## Problem

「明天早上想起要出门」这件事，最早的实现是每秒扫一遍待办表：`while true: for task in agenda: if task.time <= now: fire(task)`。三个问题同时爆出来。第一，空转烧 CPU 与额度：一天里 99.99% 的扫描都是白扫，模型不在跑也照样占着调度轮次，负载看着虚高。第二，时钟一跳就雪崩：进程被暂停十分钟再恢复，或者系统时间被校准，积压的待办在同一毫秒里全部触发，智能体一口气收到七八个「该出门了」，然后连着发七个动作，把世界搅乱。第三，自激死循环：某个待办触发后条件没真正满足（比如要求的物件还没拿到），下一轮扫描又判定该触发，再触发，再失败——调度器自己把自己烧穿，日志一秒几十行。

## Decision

把待办从「时间驱动」改成「条件驱动」，Agenda 只在条件成熟时唤醒：

1. **每条待办带显式前置条件**：能不能触发不看墙上时钟，而看条件谓词——是否到达目标地点、是否持有目标物件、用户是否在线、身体状态是否达标。条件不满足就一直挂着，不消耗轮次。
2. **条件成立才扫描命中**：Future/Agenda 的扫描由世界状态变更事件驱动（移动结算完成、拿取结算完成、会话上线），而不是固定频率空跑。没有状态变化就没有扫描。
3. **触发失败要留下退避**：条件谓词通过但执行阶段失败（比如门锁着），该待办进入退避，带次数上限与原因记录，禁止在同一条件下无间隔反复重试。
4. **丢弃不是恢复**：进程重启后待办从持久化台账重放，按当前条件重新判定——已经成熟的下次扫描命中，尚未成熟的继续等，不允许「干脆全清空重开」。

## Alternatives considered

- **死循环 while 扫描，固定间隔轮询** — 实现最简单，一个 setInterval 就行；但空转白烧资源，时钟跳变时批量误触发，还会自激成死循环。
- **丢弃全部待办，重启后重新生成** — 省掉持久化与恢复逻辑；但用户明确交代过的事（比如「晚上回来记得把水烧上」）会无声消失，智能体看起来失忆且不可靠。
- **把待办塞进提示词让模型每次自己记着** — 不需要调度器；但上下文一长就被挤掉，且无法保证按时序与条件判定，最终变成想到才做。

## Consequences

- **收益**：调度开销从「每秒一次空扫」降到「世界变了才扫」，空闲时几乎零成本。
- **收益**：时钟跳变不再造成成批误触发，触发失败有退避，自激死循环不会再出现。
- **代价与已知上限**：每条待办都必须写清楚可判定的前置条件，写得含糊（「等合适的时机」）就永远不会触发；这要求议程生成阶段就完成条件化，不能留到调度层猜。
