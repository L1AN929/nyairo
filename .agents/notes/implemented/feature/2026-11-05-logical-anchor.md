# Agent Note: 压缩日的逻辑日起点可以虚构

Status: implemented

## Problem

压缩日的逻辑时钟锚死在实例创建的真实时刻（`fastday_clock.json` 里 `logical_anchor = created_utc`）。
下午起跑就等于让她下午才起床：2026-11-05 的 x 批 13:39 走进书店时，压缩钟已经是逻辑次日 04:45，
书店 `open_hour: 10`，关着门，世界只给她换姿势的选项。同一天的 u/v 两批夜里起跑，整段白天根本
没轮到；w 批早上起跑但被门禁锁住。四批八十个请求，一大半是在替这个写死的锚点交学费。

## Decision

`prepare` 新增 `--logical-anchor`，接受带偏移量的 ISO 8601 时间（naive 或垃圾字符串具名拒绝
`LOGICAL_ANCHOR_INVALID`）。写入时只改时钟文件里 `logical_anchor` / `logical_checkpoint` /
`horizon_logical` 三个既有字段，`created_utc`、authority 时间戳、schema 版本一律不碰，写完回读校验。
夜间守卫从"看真实时刻"改成"看逻辑起点"：传了起点判起点的本地小时，没传退回判 `created_utc`，
与旧行为一致。真实时间那一侧（超时、暂停、预算、心跳、`downtime_frozen`）仍然按墙钟走，不加速。

## Alternatives considered

- **只保留起跑窗口校验，不开放虚构起点。** 最强立论：不动时钟契约，风险最小。否决原因：它要求
  实验必须在真实白天跑，而下午和夜里整段时间都不能用；x/w/u/v 四批的失败原因正是这个约束本身，
  加上守卫只是把失败提前拦下来，没有解决问题。
- **把世界包的营业时间放宽成全天。** 最强立论：只改数据不改代码，最快。否决原因：营业时间是
  "生活里真实存在的事实"，改成全天等于为了让实验通过而改写世界规则，会削弱"出门要赶在关门前"
  这个设计本身。时钟是实验参数，营业时间是世界事实，该动前者。

## Consequences

- 任何真实时刻都能把"她的一天"设在早上，实验窗口不再受按回车的时间限制。
- 逻辑时间可以领先或落后真实时间最多一个逻辑日，读日志时必须分清两套钟：life 侧 `occurred_at`
  是逻辑钟，world 侧 `transitioned_at` 和心跳是真实钟。
- 不传参数时行为逐字节不变，既有 32 条测试断言未改；新增 5 条（起点生效、不传时回归、
  夜间守卫按逻辑起点判、白天+夜里起点被拒、naive/垃圾被拒）。
- Z 批实测：真实 17:27 起跑、逻辑 08:00 落地，时钟从 08:04 正常推进，没有撞上"时间不能倒退"。
