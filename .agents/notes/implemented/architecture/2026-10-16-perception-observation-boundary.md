# Agent Note: 外界感知走单向只读事件流：严禁心智模块直接伸手改世界实体

Status: implemented

## Problem

早期为了图快，心智模块直接拿到了 World 的内存引用：想看看房间里有什么，就 `world.rooms['bedroom'].objects`；顺手发现灯太暗，就直接把 `lamp.on = true` 改掉。跑起来真的方便，但代价是灾难性的：心智侧一次“我就顺手改一下”，物理世界的坐标、物件归属、房间光照全被绕过结算层偷偷改动，台账上看不到任何因果记录；更荒唐的是心智代码里一个写错的循环，可以在一秒内把整栋房子的家具位置搅乱，事后完全无法追溯是谁改的、为什么改。加上全局共享的可变字典（`GLOBAL_STATE`）之后，两条不同的生命循环实例互相覆盖同一份状态，A 实例的“我在厨房”被 B 实例写成“我在卧室”，双方都在拿错数据做决策。

## Decision

把外界输入彻底改造成**单向只读**通道，物理世界只广播，心智只订阅：

1. **Perception 以 JSONL 单向事件流投递处境**：物理世界每个结算周期把处境（位置、可见物件、室内环境、身边的人、时间）序列化成一帧事件，追加写入只读通道。心智侧只消费帧，不持有任何 World 对象的引用。
2. **只读是硬约束，不是礼貌**：感知帧进入心智后是不可变快照。心智模块能看、能判断、能基于它生成动作意图，但没有写入口去改坐标、改物件归属、改环境值。
3. **改世界必须绕回动作通道**：想让灯亮，就必须发 `toggle(lamp)` 让执行器走真实结算；想让物件换位置，就必须发拿取和放置动作。世界只承认动作带来的变更。
4. **消费位点可恢复**：事件流带单调位点，重启后从上次消费位置续读，既不重复处理旧处境，也不会漏掉停机期间发生的世界变化。

## Alternatives considered

- **直接调用 World 实例的内存做修改** — 零延迟，改一行就生效；但等于把物理世界的边界拆了，任何模块的 bug 都能瞬间污染全局状态，事后审计无从谈起。
- **全局共享可变字典传递状态** — 写起来最顺手，import 一下就能读写；但多实例、多进程并发下互相覆盖，A 的处境和 B 的处境混成一锅，排查性能问题与逻辑问题几乎不可能分开。
- **每次感知都全量深拷贝整个世界序列化给心智** — 隔离最彻底；但一次处境快照的开销随房间物件数线性膨胀，每个决策周期都要付一次全量拷贝，跑几十轮就开始明显拖慢。

## Consequences

- **收益**：职责彻底切开，心智侧写不坏的物理世界，物理侧也不必防着心智乱伸手；出了状态错乱，一定是世界结算逻辑的问题，排查范围缩小一半。
- **收益**：事件流天然是可重放、可审计的处境日志，配合动作台账能还原“当时看到了什么、于是干了什么”。
- **代价与已知上限**：感知有一次性投递延迟，心智看到的处境总是上一帧的快照，做“抓到那一瞬间”的精细交互时必须先发动作再用新帧确认结果（动作侧的确认链路见 [动作执行必须走三段式真实结算](2026-10-16-action-reality-ledger-settlement.md)）。
