# Agent Note: 动作执行必须走三段式真实结算：拒绝代码刚发指令就假装动作完成

Status: implemented

## Problem

最初版本的动作执行就一行字的事：模型吐出一个 `move_to(kitchen)` 的调用，代码把参数塞进 World，紧接着在 Activity 记录里写一条 `status: done`，然后转头告诉模型“你已经到厨房了”。问题是物理世界根本没有动过：坐标没变、门没开、走路的那二十秒不存在，只有一条被提前写死的成功记录。这个假成功会顺着链路往下传染——下一步 `take(apple)` 在厨房的语义里被判定成功，但苹果其实还在卧室桌上；等到某个真的去核对坐标的模块（比如房间碰撞检测）跑起来，才发现位置对不上，于是整段记忆变成一串互相矛盾的谎话。更糟的是重放或重启后，Activity 台账里写着“已完成”，实体状态却是原始坐标，恢复流程直接卡死在一个不存在的中间态。

## Decision

把动作拆成「执行 → 物理确认 → 身体后果」三段，任何一段没拿到真实证据就不许往下走：

1. **AR0 只管发与收**：AR0 负责把动作意图交给 World 执行器并拿到受理回执（accepted），它不写任何“完成”标记，只记 `issued`。
2. **AR1 只听物理世界报账**：动作是否完成由 World 的结算通道说话——移动成功就是坐标真的变了，拿取成功就是持有物列表真的多了那件东西，休息成功就是体力条目真的回涨。AR1 拿不到物理证据就停在 `in_flight`，超时转 `failed`，绝不自行补一个乐观值。
3. **身体后果最后结算**：体力、饥饿、情绪这些后果是在物理确认之后由统一结算层落账，串行写一次，避免执行器一边跑一边自己改数值造成双写。
4. **失败也是合法结局**：路径被家具挡住、目标物件被别人拿走、门锁着——这些都结算成 `failed` 并把原因回灌给模型，模型下一轮自己改主意。台账允许写“没干成”，不允许写“其实没干但记成干了”。

## Alternatives considered

- **发指令直接写死成功** — 最快最省事，一行代码就能让 demo 跑得飞起；但整个世界的可信度瞬间归零，后面所有依赖位置和持有物的逻辑都建在空气上，出问题根本查不出是哪一步开始骗人的。
- **发完指令在原地轮询等物理世界回话，阻塞式等到底** — 逻辑上正确，实际把主线程钉死：物理世界一次 tick 卡顿或等到超时，整个生命循环一起停摆，比假成功还难查。
- **让执行器自己顺手把后果也改了** — 少一次结算往返；但执行器同时是裁判又是运动员，双写冲突、重启后对不齐账，最后没人知道权威值在哪。

## Consequences

- **收益**：动作的完成与坐标、持有物、数值完全对齐，重启后重放台账能拿到一致状态；模型看到的“我做到了”一定是真的做到了。
- **收益**：失败有明确出口，模型能根据失败原因换方案，而不是在假成功上继续堆叠无效动作。
- **代价与已知上限**：每个动作多一次结算往返与一个 `in_flight` 状态位，实现比一行写死复杂得多；等待期间需要一个稳定的超时与取消路径，否则会积压挂起动作（房间内交互的真实几何约束见 [房间家具必须有真实坐标与碰撞体](../feature/2026-10-16-room-interior-furniture-perception.md)）。
