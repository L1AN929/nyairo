# Agent Note: 资源与算力必须单次凭证授权：防重放攻击与跨会话透支

Status: implemented

## Problem

资源消耗最初是“给额度就随便花”的模式：会话开始时给智能体挂一个额度池，想推理几次就推理几次，跑完到月底再看账单。这个设计在单机演示时看不出毛病，一旦跑真实生命循环就炸：一次卡住的循环在十分钟里把额度烧光，因为没有任何单次请求的代价感；更致命的是一条被重复提交的推理请求可以把同一份额度反复兑现——请求体是重放来的旧请求，额度池只认“还有余额”而不认“这张凭证用过没有”，于是同一份额度被扣成了负数，或者更常见的是：扣了但没记录到底是谁花的，账单对不上，运维只能靠猜。跨会话时问题翻倍，上一个会话的残留额度被新会话继承下来，新生命一开局就以为自己很有钱。

## Decision

把每一次资源消耗都变成**凭单次凭证（Ticket）兑现**的过程，Governance 层做唯一裁判：

1. **先领票，后花钱**：模型推理、工具调用、任何计费动作，必须在发起前向 Governance 申领一张单次 Ticket；Ticket 自带额度上限、用途标记与 epoch。没有票的请求一律拒绝，直接打回。
2. **一票一次，用过即废**：Ticket 在兑现时被原子标记为已消费；同一张票第二次提交直接判定为非法（防重放），不做“再扣一次算了”的宽容处理。
3. **epoch 隔离，跨会话不继承**：每次生命周期启动有独立 epoch，旧 epoch 的票与余额在新 epoch 下全部作废。重启后不会“继承上一个会话的剩余额度”，新生命的资源账本从零开始记账。
4. **扣减必须留痕**：每次兑现落一条可审计记录（票号、用途、消耗、余额），出问题能定位到具体哪一次推理烧掉了哪一段额度。

## Alternatives considered

- **给固定额度、不验任何凭据** — 实现最省事，一个计数器就够；但重放请求可以把额度盗刷成负数，而且完全无法定位是哪一个动作烧的。
- **无限透支、按月对账** — 短时间体验最自由，模型想推几次思就推几次；但一个死循环的夜晚能烧掉整月预算，而账单要月末才看得见，等发现时已经晚了。
- **每个请求都重新走一次完整审批流程（含人工确认）** — 安全到极致；但把交互节奏彻底掐死，日常推理每次都要等人点头，无法支撑连续的自主生活。

## Consequences

- **收益**：任何一次资源消耗都能追到具体票据，重放攻击在兑现这一步就被挡掉；预算超支从“月底发现”提前成“当场拒绝”。
- **收益**：epoch 隔离让重启行为干净，旧会话的残留不会污染新生命的账本。
- **代价与已知上限**：每个计费动作多一次申领往返，延迟略增；Ticket 的原子兑现必须真的原子（同进程多协程、跨进程都要挡住），只靠内存标志位等于没做（并发写入的隔离原则见 [多个 AI 干活必须独占写代码](2026-10-16-single-writer-isolation.md)）。
