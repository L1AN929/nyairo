# Agent Note: 修复模型推理死锁：暂停状态下释放共享锁，防止前台活动卡死

Status: implemented

## Problem

在 W05R 测试时发现一个致命 Bug：当系统进入 Pause（暂停）状态调用大模型生成文本时，代码一直霸占着全局读写锁不放。大模型流式生成往往需要十几秒甚至更久，导致后续的前台活动在等待这把锁时直接超时崩溃，或者抛出 `ADOPTION_REJECTED` 拒绝执行。等模型回复完，智能体已经卡死在原地，根本动不了。

## Decision

彻底重构锁的释放时机：
1. 发送完请求立刻丢锁：只在组织 Prompt 和建立连接的那几毫秒里持锁，一旦网络请求发出去、等待模型 token 返回，立刻把锁释放掉。
2. 回调返回重新校验：模型生成完毕拿到结果后，重新加锁并校验环境版本号，确认数据没冲突再写入。
3. 前台活动通行无阻：大模型在后台慢慢推理，前台生命状态机可以正常流转，不再被长耗时请求拖死。

## Alternatives considered

- **维持原本的长事务大锁，只把超时时间调大到 60 秒** — 纯粹掩耳盗铃，网络只要一卡照样超时死锁，且前台整个被冰冻，用户体验极差。
- **完全去掉锁机制，大家随便并发写** — 虽不卡死，但模型返回的数据会把前台刚更新好的新位置和新状态给随机覆写掉，产生幽灵数据。

## Consequences

- **收益**：大模型生成哪怕耗时 30 秒，前台也绝不再卡死，状态恢复成功率直接拉满。
- **代价与已知上限**：模型返回时需要额外判断一下“我发请求时的旧状态，在拿到结果时有没有被用户改动过”，多了一层状态对比逻辑。
