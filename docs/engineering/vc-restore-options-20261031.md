# V-C 恢复权威：剩余选项分析（2026-10-31）

**结论：V-C 整体仍未过。当前已有一条有限、可用的恢复链，但本次未证实已接入能抵抗整机回滚的独立控制新鲜度根。**
本文件只收敛选项、交给本人裁定，不实施任何恢复合同、权限或存储变更。

## 一、先校准当前事实

不沿用 10-26「六文件内没找到恢复入口/权威」的结论——那只覆盖当时扫描范围。10-28 已落地的部分：

- `memory_authority` + `.floor.json`：删除前先推进受信下限；底账必须显式放在实例业务根之外，落在根内直接拒绝。
- `scripts/forget_request_cli.py` 的 `request / status / retry / confirm / recover` 与 `RecoveryGate`：未激活的恢复副本读写都返回具名 BLOCKED；marker 绑定 controls 路径与 sha256；authority 前进后要求重新扫描。
- typed 来源权威与 `erase_source` 逆向闭包：同源换 event id 重投被拒，M0 正文物理擦除，Practice/Sharing 的版本正文与投影一起清。
- 停服后三库同路径回填 + 登记投影重建：被删内容不可读、无关内容保留、新写可用。这是已被父级限定接收的一条恢复用法。

仍然成立、必须原样保留的边界：

- 现有本地 authority/floor 的同域整体回滚不在保护承诺内；本次没有核实际部署的备份/权限配置，不能据默认布局断言所有部署必同域。同机换目录本身不能证明独立。
- 未登记派生面、旧无血缘投影、在线文件替换、直接 OS 读文件均不在保护内。
- 删除前备份仍含正文，主 case 停在 `WAITING_RETENTION`，不是「所有副本已消失」。
- `readingpractice` 精确 1 例仍红，归因 UNKNOWN/STOP，未洗绿。
- proposed 笔记里的 `LEGACY_HISTORY_UNKNOWN` / `IMPORTED_LOCAL_LEDGER` 精确常量在本次扫描中未找到，不能仅凭常量缺失断言所有等价迁移能力都未实现；旧实例迁移与历史完整性处理仍未在本次验证。

历史旧双库回滚 FAIL 是历史事实，本次不重跑；也不能反过来把它写成「任意回滚都会复活」。

## 二、三个选项

### ① 保留现有能力边界，不承诺跨备份/整机回滚

**最强理由**：零新增存储、零新合同，今天就能避免把「逻辑扣留 + 同路径恢复」宣传成恢复安全。诚实边界本身是有价值的交付，且不构成永久放弃设计要求。

**代价与可用性**：缺陷仍在。旧 evidence、旧 controls 与旧 authority/floor 一起回退时，本机无法自证最新。可用性没有额外损失，但也换不来保护。

**信任与故障假设**：只信任「同一可信根没被一起回滚」这一前提；不假设管理员权限与备份权限分离。

**需要本人批准**：无新合同。只需接受「V-C 仍 FAIL」的对外表述边界。

**可说明的损失**：能列出已扫描范围、已知复活条件和未覆盖派生面；不能给出具体被丢掉的删除历史，也不能说删除合规成立。

**UNKNOWN**：真实旧实例的现场形态、非 SQLite 备份工具、外部副本。

### ② 恢复时必须提供可信且足够新的 controls/高水位，不可得则 fail-closed

**最强理由**：如果确实存在一份不随业务回滚的可信来源，可以直接复用现有 authority 投影、floor 比较和 `RecoveryGate`，不必先重建 Memory 或新增整套服务；②可以独立成立，逻辑上不必然引出③。

**核心待答问题**（也就是这个选项真正的成本）：谁保存这份事实、谁证明它「至少和最新删除一样新」。人工签名只能证明签署者的主张，不能单独证明最新；数字 epoch 能检测陈旧后整段阻断，但不足以单独恢复逐项删除集合；从待检副本自身历史推出来的时间会随文件一起回退。

**代价与可用性**：需要新增或明确恢复合同、激活门与新鲜度来源。取得不到证明时，相关 Memory 读取全部扣留——这是明确的可用性损失，必须由本人接受，不能用「UNKNOWN 但仍回正文」糊过去。

**信任与故障假设**：来源的写权限、备份策略、故障模型必须独立于业务回滚；仅「另一个目录」不满足。

**需要本人批准**：恢复合同（谁签发新鲜度、恢复范围如何界定）、恢复入口/激活门的新增语义；若涉及新持久格式，另批。

**可说明的损失**：能报告哪些范围因新鲜度未证而扣留、已核对到哪个权威头；未知删除历史仍须标 UNKNOWN。

**UNKNOWN**：现树及实际部署是否存在合格来源尚未证实。floor 与底账若随同一恢复操作回退，就不能互证最新；环境变量 `NYA02_MEMORY_AUTHORITY_MIN_SEQ` 只是操作者交接值，其值本身不构成独立新鲜度证明。

### ③ 建立或复用业务回滚域外的控制权威，含删除范围与 writer fence（新合同）

**最强理由**：对应设计 17 章 §5.5 的原文要求——writer/delete/revocation 高水位必须在业务回滚域外，控制 ledger 也丢则只读阻断。只有真独立的域外权威才能在整机回滚后仍然说「你少了哪些删除」。

**它与②的关系**：③是把②的前提真正做出来，不是二选一的对立面。若已有合格外部来源，②无需新 store；若没有，②只是要求，必须由③补上来源。不要为了「看起来完整」先建 store 再补信任模型。

**代价与可用性**：新增权威存储、客户端与运维；删除与读取都依赖权威可用，权威不可用时 DELETE 不能报成功、相关读取受阻。需要定义：持久化一致性、幂等键、writer fence、激活、authority 丢失/回滚、loss report、保留策略和恢复范围。控制信息只存元数据，不存正文。

**信任与故障假设**：必须证明备份、恢复、管理权限和故障模型下与业务真正独立——独立账号、独立介质或独立主机，且备份策略不被同一管理员一次性回滚。不能承诺同机独立目录绝不回滚。

**需要本人批准**：新合同、新权限边界、新存储与部署方式；旧实例是否接入、迁移语义。

**可说明的损失**：能以稳定身份说明权威确证过哪些范围、备份落后何处、哪些内容因此未激活；不能恢复已经丢失的事实，也不能撤回已经外发的副本。

**UNKNOWN**：完整派生面、跨主机一致性、权威自身的灾难恢复。

## 三、推荐的分阶段方向（未实施）

先做**来源可行性判定**，再决定走②还是③：

1. 维持①的诚实边界，对外只说「同路径、已登记派生面有限保护」，不承诺整机回滚。
2. 用一个只读、有界的核查回答：现网/部署里是否存在一份确实独立于业务备份、且能证明新鲜度的控制来源。若存在，②可以单独成立；若未证实来源存在，就保持该前提 UNKNOWN；只有确认需要新来源、且本人另行批准信任合同后，才进入③的设计或施工，不自动新建 store。
3. 若本人批准③，最小合同按「append-only 控制记录 + 显式新鲜度交接 + 恢复激活门 + loss report」落地，并保留「合法未删经历可读」的正控，避免用一律拒绝冒充修复。

## 四、最窄决策题

**若要求抵抗 authority/floor 也被回滚，是否接受由独立可信来源证明控制新鲜度，并在证明不可得时阻断相关读取与删除成功声明？** 保管方、恢复范围、存储和旧实例处理是后续需分别明确的合同项；不把具体部署方式、迁移政策或新状态名随这一问默认批准。

如果不批准，就停在①，继续如实标 V-C FAIL；如果批准，先交来源可行性结论，再定②或③的施工范围。这两个是不同层级的决定，不要用「继续做」默认把新合同带进来。

## 五、未来验收建议（本次全部未跑）

获批后至少覆盖，并按 PASS/FAIL/BLOCKED/UNKNOWN 分别报告：

- 旧双库（evidence + controls）同回滚，authority 保留新删除 → 仍扣留。
- authority 与 floor 一起回滚 → 具名阻断，不静默放行。
- controls 缺失/损坏/错 owner → BLOCKED，不退化成「没有过去」。
- 新鲜度不可得、权威头落后、序列断裂 → fail-closed，且不得返回正文。
- 旧 writer 晚到写 → 被 fence 拒绝。
- 派生重建（Practice/Sharing/Supply/登记投影）后仍不复活。
- **正控**：未被删除的经历在恢复后仍可读、新写可用——不能靠一律拒绝所有恢复冒充通过。

不拿这套建议当已执行，也不拿 G1 或 24h 验收替代 V-C。
