## 一句话结论

**现在无法证明存在一份独立于业务回滚的新鲜度来源。** 现有 `memory_authority` + `.floor.json`
只是「放在实例业务根之外」，这是布局要求，不是独立性证明；同一台机、同一套备份、同一个管理员
能一起回滚它，它就无法证明自己是最新的。

所以 V-C 仍 FAIL，且**不能靠现有件直接升级成通过**。

## 判断「合格来源」的四条

以下四条是**当前威胁模型下的拟议判据**，不是唯一已定的技术合同：物理独立、管理员角色分离只是
其中一种实现方式，别把它当成已经拍板的唯一标准。

1. **写权限独立**：恢复业务数据的人不能同时改写这份来源。
2. **介质/主机独立**：不与业务库同一次备份、同一个快照集。
3. **可证新鲜**：能回答「这份控制状态至少和新近一次删除一样新」，而不只是「我没有被改过」。
4. **故障时 fail-closed**：来源不可读或落后时，相关读取扣留、DELETE 不得报成功。

对照现有件：

| 现有能力 | 满足哪几条 | 缺什么 |
| --- | --- | --- |
| `memory_authority` + `.floor.json`（业务根外） | 3 的弱形式（floor 前进可比） | 1、2 未知；同机同备份时 3 也会一起回退 |
| `RecoveryGate` / `forget_request_cli recover` | 恢复入口本身 | 不提供来源；未激活时 BLOCKED 是好的 |
| `NYA02_MEMORY_AUTHORITY_MIN_SEQ` 环境变量 | 人工交接值 | **不构成新鲜度证明**：值可被一起回滚或人工填错 |
| typed 来源擦除 + 三库同路径回填 | 删除/恢复执行面 | 不解决「怎么知道少了哪些删除」 |

## 能用、但必须明说弱在哪的两条路

**路一：复用现成的外部只读副本（如果部署里真有）。**
代价最低，若确实存在与业务备份分离的副本（另一主机/账号/介质上的 authority 或删除日志），
②就能单独成立，不必新建服务。**前提是本次核不清它是否真的独立**——目前 UNKNOWN，不是「没有」。

**路二：人工签认的新鲜度交接。**
由人声明「权威序列至少到 N」，恢复时比对；不满足就 fail-closed。
**它的地位要说准**：这只是「若将来立信任合同，可以纳入的一个备选」，**不是已验证今天可用**，
**也不能替代独立新鲜度证明**——人工声明证明的是签署者的主张，不是「这份状态确实最新」。
「诚实时点」怎么定义、那份声明的最新值由谁独立保存、怎么防它和业务一起被回退，都还没有答案；
在这些问题答上来之前，这条路本身仍是 UNKNOWN。
**代价**：每次恢复都要人工在场；能防「不知道被回滚」，防不了「有人同时改业务和声明」。

**不建议**：为了看起来完整先建新权威服务再补信任模型——那正是 10-26 方案里被否掉的做法，
换成域外主机也不自动合格。

## 要落实「有没有独立来源」，只读能查的四件事

1. authority/floor 在部署里**物理**落在哪：同机？同备份集？同一挂载？
2. 有没有任何**删除事件**被同步到业务库之外（外部日志、监控、审计流）。
3. 谁是能同时回滚业务与 authority 的账号：同一人/同一角色即判不独立。
4. 备份策略是否把两者放在同一快照里。

这四项都是部署事实，**代码读不出来**，本次没有核，全部记 UNKNOWN。任何一项答不上来，
只能说**「不能认它为合格来源」**，不等于已经证明它客观上不存在、或客观上不独立；
也不能靠「应该分开」放行。

## 给本人最小的话

方向可以批，但**「现有来源够不够独立」这个问题现在还答不了**，需要有人去核部署事实（上面四项）。

- 查不清 → 停在①，对外继续如实说 V-C FAIL。
