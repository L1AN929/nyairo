# v0.4 work-revisit 收尾施工方案（监工版）

> 用途：本方案是给总监工代理的执行简报。监工只读、只派工、只验收，不直接写业务代码。
> 生成日期：2026-10-21。对应结果文档：`docs/engineering/v04-work-revisit-result.md`。

## 一、角色与边界

- 总监工负责：拆任务、派子代理、审改动、跑门禁、汇报。
- 总监工不负责：直接编辑业务代码、绕过子代理手改、替用户拍板产品问题。
- 子代理负责：在指定写集内完成实现与自测，回报改了哪些文件、跑了什么、结果如何。
- 任何时刻只允许一个代理写入同一文件。并行只在写集完全不相交时开启。

## 二、范围

只做 v0.4 work-revisit 剩余四项，按下列顺序推进：

1. **手机界面接历史路由**（纯前端）
   服务端已有 `GET /api/phone/projects/<id>/versions`、`GET .../versions/<vid>`、
   `GET .../versions/<vid>/compare`、`POST /api/phone/projects/derived`。
   `components/phone/web/app.js` 目前没有任何请求打到这四个路由。
   要做的：版本列表、单版本正文、两版对比、从选定旧版派生新作品。
   必须保留原有三态：未连接、缺失、错误；不得 mock 数据。
2. **Edge 端真实验证**
   用 Edge 打开手机面板，走完「看历史 → 对比 → 派生」链路，记录实际观察结果。
   不以单元测试代替这一步。
3. **Life 写作上下文接入**
   让写作流程能引用历史版本作为上下文。涉及主循环，风险最高，单独派工、单独验收。
4. **runtime 重启验证**
   重启后历史版本仍可读、可对比；派生作品仍在。

第 2 项依赖第 1 项完成。第 3 项可与第 1 项并行，但写集必须不相交。第 4 项最后做。

## 四、派工方式

监工用 `scripts/dispatch_worker.py` 拉起施工模型，任务正文写进文件后传入：

```bash
python scripts/dispatch_worker.py --name phone-history --task-file /tmp/task-a.md
```

默认施工模型 `workbuddy-wg/cn:deepseek-v4.1-flash`，网关 `http://127.0.0.1:3425`，
可用 `--model` 覆盖。worker 交付原文落在 `.agents/worker-runs/`。

## 五、对子代理的硬要求

- 先读文件再改，禁止凭猜测改接口。
- 一次给足一整块任务，不要切成十几个碎片来回问。
- 不做与任务无关的重构、不顺手改风格、不新增依赖。
- 不过度校验：不为了“证明完整性”去算 SHA256、不逐字节比对历史文件；测试要求的除外。
- 服务端契约不够用时停下来上报，不许擅自改服务端契约。
- 碰到承重墙（例如强制打卡类设计）一律停，先问用户。
- 交付时说明：改了哪些文件、跑了哪条命令、结果是什么、还有什么没验证。

## 六、门禁与验收

- Python：`python scripts/test.py`，至少覆盖 host-boundaries 与 cognition-faults 两套；
  以及 `tests/test_v04_work_revisit_history.py`、`tests/test_v04_work_revisit_writer_chain.py`。
- 前端：仓库内前端测试全跑，报告通过数。
- 若产生新决策笔记，跑 write-notes 的格式与树校验脚本，红灯即视为未达标。
- 验收以「真实跑过」为准，不以代码看起来对为准。

## 七、停止条件

出现以下任一情况立即停手并汇报，不自作主张继续：

- 需要修改服务端路由或落盘格式。
- 同一处测试连续两轮不过且原因不明。
- 需要改动既有基石决策。
- 前端需要新增全局状态管理或大改架构才能接上。

## 八、开工前需要用户拍板的问题

1. 历史版本列表每页多少条，默认是否只显示最近 10 版？
2. 从旧版派生的新作品，是否自动在正文里标注来源版本？
3. Life 写作引用历史时取最近几版，是否允许用户手动指定？
4. 这一轮是否接受「前端先接上、Edge 验证下一轮再做」的分批交付？
